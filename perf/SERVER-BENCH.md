## What this measures (and what it deliberately does NOT)

The companion micro-bench (`perf/bench.mjs`) measures the DataAccessor through the **authenticated**
CSS request path. This harness instead measures the **server-level storage delta in isolation**: it
boots a full CSS in three storage configurations and drives anonymous `oha` load at them.

**Auth is removed from the measurement on purpose.** Each config uses CSS's `allow-all` authorization
+ a writable root, so every request is anonymous — no DPoP, no token, no WAC/ACL evaluation. The goal
is the **storage-layer** delta (the cache's effect), not the auth/DPoP/WAC overhead (which the Rust
bench measures separately and which would otherwise dominate and mask the storage signal). The numbers
therefore reflect: CSS's HTTP + LDP framing + the storage backend — with the only difference between
the three configs being **the storage backend itself**.

## Config matrix

All three configs are full bootable CSS servers based on `css:config/file-root.json` (writable root,
no account registration), with exactly two controlled swaps: authorization `webacl` → `allow-all`, and
the storage backend per row. Same CSS version, same machine, booted one at a time on separate ports,
back-to-back. Configs live in [`perf/server-configs/`](server-configs/).

| config | storage backend | what it isolates |
|---|---|---|
| **A — cached-file** | `CachingDataAccessor` → `FileDataAccessor` (this package; NEW defaults: 1 GiB / 1 MiB read cache, 100 MiB write-back queue) | the cache in front of the file backend |
| **B — plain-file** | stock `FileDataAccessor`, no cache | the plain-file baseline |
| **C — in-memory** | `MemoryDataAccessor` | the upper-bound ceiling (no disk) |

The **A-vs-B** delta is the **cache benefit over plain file**. The **A-vs-C** delta is **how close the
cache gets to the in-memory ceiling**.

## Workloads

`oha` concurrency sweep, `-z` duration per level, one discarded warm-up per workload, anonymous:

1. **hot-read** — repeated `GET` of the **same** small resource (`/bench/hot`). The cache-**HIT** path:
   the read cache is **warmed** with a few GETs before the measured sweep, so for config A every
   measured GET is served from memory (queue → cache → *hit*), never touching disk. This is where the
   cache should most clearly beat plain file.
2. **cold-read** — `GET` across **many distinct** resources via `oha --rand-regex-url`, churning a
   random path per request across the **entire seeded set** (`/bench/cold/res-NNN`, every one of which
   **exists** — the harness verifies the churn bounds return 200, so this measures real reads, never a
   404 path). Exercises the cache across many keys + LRU.
3. **write** — `PUT` of a distinct churn path per request (`/bench/write/w-NNNNNNN`, 256 B body). The
   write-**back** path: config A's queue acknowledges the write in memory and flushes to disk on a
   background worker, so it should ACK faster than plain file until the queue caps. The write area is
   reset between configs so the runs are comparable.

## Interpretation

Read this in light of the load caveat above — **directions are reliable, exact magnitudes are an upper
bound** (config B ran under the worst contention, which inflates the A-vs-B figures).

- **The ordering is consistently C > A > B on every workload at every concurrency level** — exactly the
  physically-expected result: the in-memory store (C) is the ceiling, the cache (A) sits between it and
  plain file (B), and plain file is slowest. That the ordering never inverts across 36 measured cells —
  even with the load swinging between configs — is the load-robust takeaway: **the cache is a clear net
  win over the plain file backend, and a meaningful step toward the in-memory ceiling.**

- **hot-read (the cache's home turf):** A (cached) sustains **+52% to +416%** more RPS than B (plain
  file) — the warmed single resource is served from memory on the cache, while plain file re-reads +
  re-parses it from disk every request. A reaches **~22–54% of the in-memory ceiling (C)** — it closes a
  large fraction of the file-vs-memory gap without giving up durability. p50 latency on A is a fraction
  of B's at every level (e.g. c=64: A 155 ms vs B 1020 ms).

- **cold-read (many distinct keys):** A still beats B substantially (**+198% to +512%** RPS). With the 1
  GiB default cache the 1000 × 256 B set fits entirely in cache after warm-up, so this is a *many-key
  warm-read* rather than an eviction-churn — the cache absorbs the working set and the per-key lookup is
  far cheaper than B's per-request disk read + parse. A reaches **~19–30% of C** here (a smaller fraction
  than hot-read: spreading reads over 1000 keys costs more per-key bookkeeping than hammering one).

- **write (the write-back path):** A (queue ACKs in memory, flushes on a background worker) beats B
  (synchronous disk write per request) by **+48% to +147%** RPS, with roughly half the p50 latency at
  every level — the write-back queue removes the synchronous disk write from the request path, as
  designed. A reaches only **~9–20% of C** on writes: the in-memory store has *no* disk write at all,
  whereas A still has to *eventually* flush, and the write tail (p99) climbs under load as the background
  flusher competes for the (heavily contended) event loop — the cooperative-flush dynamic the micro-bench
  documents. The write-back win over plain file is real but smaller than the read win, and most valuable
  at higher concurrency where plain file's synchronous disk writes serialise hardest.

### Bottom line

On a full CSS server with auth stripped out to isolate storage, the `CachingDataAccessor` (config A) is
a **clear, consistent win over the plain file backend (config B)** on reads and writes alike, and closes
a substantial part of the gap to the **in-memory ceiling (config C)** on reads (less so on writes, where
the queue still owes a flush that in-memory never does). The exact percentages from THIS run are
load-inflated and should be re-measured on a quiet box; the **direction and the qualitative shape** (big
read win, solid write-back win, reads closer to the memory ceiling than writes) are the trustworthy
conclusions.

## Reproduce

```bash
brew install oha             # or: cargo install oha   (a local DEV tool, NOT a project dep)
bash perf/setup.sh           # the SAME out-of-repo CSS runtime the micro-bench uses
bash perf/server-bench.sh    # boots A, B, C in turn; seeds; runs the oha sweep; prints the TSV
# then: python3 perf/render-server-bench.py   # renders the result tables for this doc

# knobs (env):
#   BENCH_CONCURRENCY="1 8 32 64"  BENCH_DURATION=10s  BENCH_WARMUP=3s
#   BENCH_COLD_SET=1000 (power of ten)  BENCH_BODY_BYTES=256  BENCH_MIXED=0
#   BENCH_PORT_A=3020 BENCH_PORT_B=3021 BENCH_PORT_C=3022
```

### Why `COLD_SET` is a power of ten

The cold-read churn regex is `res-[0-9]{WIDTH}` where `WIDTH` is the digit-count of `COLD_SET`. For
the regex to span **exactly** the seeded resources (so every random churn URL hits a resource that
EXISTS, rather than a 404 — which `oha` would silently count as a "success"), `COLD_SET` must be a
power of ten; the harness validates this and fails loudly otherwise. The harness also probes the first
+ last resource of the range after seeding and aborts if either is not `200`.

### A note on the read cache vs the cold set

With the NEW defaults (1 GiB read cache) and 1000 × 256 B resources (≈ 256 KB total), the **entire**
cold set fits in the read cache after the warm-up. So config A's "cold-read" is, in steady state, also
a largely-cached workload — it measures the cache's behaviour across *many keys* (LRU bookkeeping,
admission, per-key lookup) rather than a true eviction-churn. To force genuine eviction churn, shrink
the cache (a smaller `maxReadCacheSize` in `server-configs/A-cached-file.json`) or raise `COLD_SET`
past what the cache holds. The default run reflects the realistic "working set fits in cache" case,
which is the case the cache is designed to win.
